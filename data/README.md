# Sample data

All of the files in this folder are made up for a prototype. They are not Humana documents, and they contain no real member, provider, or claims data. Harbor Health is a fictional plan name. Any number in these files is illustrative.

`rx_education_script.md` is a messy pharmacy education call script for a Medicare Advantage line. It has a greeting, a pricing disclaimer, a closing, advocate notes, and lines marked Verbatim (Legal). One paragraph mixes the verification steps with the rule about what an advocate may quote. This is the document an author would upload first.

`rx_education_script_v2.md` covers the same kind of call. Its pricing disclaimer changes a few words and keeps the same meaning, so a near-duplicate check should pair it with the first script. The mail-order rule in this file conflicts with the first script. The closing line and the specialty-pharmacy line are copied exactly, so an exact-match check has something to find.

`website_faq_excerpt.md` is a short member-facing website excerpt. It carries a third wording of the same pricing disclaimer, for the scenario where today's search returns three documents and three wordings.

`search_log.csv` is about 20 queries an advocate might type, with the columns query, role, and timestamp. It includes shorthand and acronyms (MA, PDP, MOOP, Rx, OOP, formulary, tier), a few misspellings, and questions from both the Pharmacy advocate and the Insurance advocate. Five of the queries cannot be answered from these documents. Two of those five are asked more than once, so they form blind-spot clusters: prior authorization turnaround time, and the plan MOOP.

`roles.json` is the role-to-knowledge-base map from the prototype spec. The Knowledge Ops author can read and write every knowledge base. The Legal / Compliance approver can read every knowledge base. The Pharmacy advocate reads pharmacy and shared-legal. The Insurance advocate reads benefits and shared-legal. Member chat reads units marked for members in pharmacy or benefits. The Knowledge owner sees analytics only.

`benefits_cost_guide.md` is a short, slightly messy guide for Insurance advocates. It lives in the benefits knowledge base. It has one verbatim cost-estimate disclaimer for a medical visit, marked Verbatim (Legal), and one benefits policy about specialist referrals. The $35 training copay in that policy is illustrative. The guide does not answer the blind-spot questions in the search log.

`kb_assignments.json` records the knowledge base and audience for each expected unit. The pricing disclaimer, the verification units, the mail-order rule, the specialty rule, and the greeting sit in pharmacy. The website FAQ disclaimer is merged into the canonical pharmacy disclaimer, and that unit's audience is advocate and member. The closing sits in shared-legal so both advocate roles can retrieve the same unit. The medical cost-estimate disclaimer and the specialist referral policy sit in benefits.

`golden_set.csv` holds 15 evaluation questions, with the columns question, role, expected_unit, expected_before_resolution, why, and heldout. Twelve rows are the scored set (`heldout=no`). Three rows are held out (`heldout=yes`): a specialist-referral question, a caregiver-authorization question, and a tiering-exception turnaround question. Those three were written from the source documents before the model saw them. Expected units are descriptive placeholders (for example U-RX-PRICING-DISCLAIMER) to reconcile after extraction. `expected_before_resolution` matches `expected_unit` on every row except the two mail-order questions, which are ABSTAIN while that conflict is open. The set includes answerable questions, questions that should abstain, a misspelled question, an acronym question, and two cross-role leak tests where a pharmacy unit must not appear for the Insurance advocate. It also includes an Insurance advocate question whose answer is the benefits cost-estimate disclaimer, and the same closing question for both advocate roles, who should both receive U-RX-CLOSING. Figures from this file are illustrative.

`human_decisions.json` holds the human inputs the demo applies: knowledge base per unit, audience corrections, the canonical pricing unit, the website merge, member wording for every unit the model marked audience both, the prepared conflict resolution, the channel revision for the advocate text and the member text, and the drift edits. Scope and audience come from this file, keyed by unit id. The held-out questions and the five harder dedup labels are recorded here as choices made before the model ran. `explore_feedback` holds eight illustrative feedback records that the Explore sandbox loads.

`member_data.json` is the mock plan-data service for the Explore member site and the advocate record. It holds the Harbor Medicare Advantage HMO schedule, a seven-drug formulary with illustrative prices, three fictional pharmacies, and one record for each caller in the advocate scenarios. Dana R. (`HBR-20418`) is the signed-in member. Every dollar amount in the file is illustrative. The file does not contain approved wording. That wording stays on the knowledge units.

`dedup_variants.csv` holds 20 made-up variants of the pricing disclaimer, with the columns variant_text and label. The label is either duplicate or meaningfully_different. The first 15 change punctuation, filler words, or phrasing, or they change the days' supply, the pharmacy type, the guarantee, a dollar condition, or who the estimate applies to. The last 5 are harder: a reordered sentence, a single change from can to may, any retail pharmacy, thirty-day written out, and a weakened guarantee. The file is for measuring near-duplicate precision and recall. Figures from this file are illustrative.
